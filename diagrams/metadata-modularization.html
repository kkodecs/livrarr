Livrarr — Metadata Pipeline Modularization

Target architecture (the next arc) — split the tangled work-creation + metadata pipeline into clean, compile-walled subsystems. Decisions locked in a PO design session, 2026-06-02 (Q1–Q7). Seed doc: design-metadata-modularization.md

COMPANION This is where the pipeline is going. For how it works today — the current spine, the six forks, and the WCC fixes — ▶ open metadata-lifecycle.html
THE ONE IDEA — READ THIS FIRST
One pipeline, three concerns, identity flowing one way. Today, identity resolution + provider fan-out + merge + status + cover are all fused in one enrich_work spine — which is why a cover bug stalls enrichment and a late anchor breaks a provider. Split them: Identity ("what work is this?") gates Enrichment ("fill the record"), which feeds Materialize ("project it onto files"). All three sit on one shared Provider-Access pipe. The boundary is compiler-enforced — the two subsystems literally cannot see each other.

1 · The architecture — four crates, arrows point down

Every dependency points toward livrarr-domain (the existing workspace rule). Identity and Enrichment are non-dependent siblings — they talk only through the contract type that lives in domain, so one-way is a thing the compiler won't let you break.

2 · One-way + monotonic identity Q1

Identity → Enrichment, never back. Convergence lives inside Identity. Anchors are durable — three write-paths, and only one can change an existing anchor:

ADD · automatic
New anchor type → append

A lookup finds an anchor the work lacks → just add it. Never touches an existing one. This is convergence — and why one-way is safe.

CONFLICT · automatic
Contradicting anchor → raise

A lookup finds a different anchor of the same kind → surface a Conflict for the user. Never silently overwrite.

EDIT · user only
The only mutation path

The user explicitly changes an anchor. An ID-edit re-fires enrichment (old metadata may be the wrong book) — preserving user-set fields. Still one-way: the edit just re-opens the gate.

NEVER
volumeId as identity

A GB volume id is an edition-level dead-end — never an anchor (ST-002). ISBN is the de-facto identity; the residue is needs-review.

3 · The contract — identity, never metadata Q3

What Identity hands Enrichment is a thin record — the library catalog card (the call-numbers to find everything), not the book. The field data lives in the shared cache; only identity crosses the boundary.

EstablishedIdentity — crosses the boundary

struct EstablishedIdentity {
  work_id,
  anchors:  { ol_key, gr_key, hc_key, isbn_13, asin },
  title, author, language,
  state, method,
  generation,   // bump → re-enrich

4 · Two state machines + the gate Q4 · Q5

The single overloaded EnrichmentStatus splits into two independent tracks. This is what structurally kills the WCC conflation: "which book is this?" (Identity) vs "we know the book, found no info" (Enrichment) become different states with different user actions.

Identity — "what work is this?"

resolution lifecycle
Pending→ Confirmed Provisional Conflict NeedsReview

Provisional = ISBN resolved, no canonical work anchor yet (keeps trying to upgrade). Conflict/NeedsReview await the user.

Enrichment — "how filled-in is it?"

fill lifecycle
Unenriched→ Enriched Thin

Enriched = identity + ≥1 meaningful text field (cover may still arrive). Thin = identity is fine but we found almost nothing → flag for the user.

The gate — Enrichment runs only on a deterministic key

Display (show the best in hand) is never gated; only the provider fan-out is.

Identity stateEnrichment fan-out
Confirmed✅ enrich
Provisional (ISBN, no anchor)✅ enrich — the whole point of Provisional
Pending (fuzzy, no key)⏸ hold — converge first
Conflict⏸ pause — user resolves
NeedsReview⏸ hold — user resolves

Re-fires on a generation bump (a new anchor → better providers; a user edit → redo).

5 · Why three boxes — Materialize is its own concern Q6

Decisive reason (cross-family confer — Gemini): cardinality. Enrichment is 1:1 with the Work (logical, DB-centric, network-bound, slow). Materialize is 1:N with physical files (disk-bound, fast, fragile). Binding them forces the network pipeline to manage file paths + I/O state — and an OOM in the tag-writer would stall the canonical DB enrichment. Split, the record stays correctly enriched no matter what; only the file-projection retries.
🛟 Failure isolation

The audio tag writers OOM on big files (m4b/mp3 tagging currently disabled). Isolated, a tag-write blowup can't take down enrichment.

🎯 Different triggers

Import a second file for an already-enriched work → write tags, but don't re-enrich. Idempotent via tag_generation < merge_generation.

🧱 Compile-wall win

The import/library path depends on livrarr-materialize without pulling Enrichment's network/LLM stack.

🖼 Cover = special, eager

The most important class — never an identifier, but fetched first so it's there at creation. Materialize exposes a sync materialize_cover() (UI blocks) + an async materialize_tags() (heavy disk).

6 · Sequencing — WCC is phase 1 Q7

This isn't a competing effort. WCC already builds the seams this arc extracts — it just builds them inside livrarr-metadata. Land it, then relocate.

① WCC (now)Federated IdentityResolver, payload cache, GR ladder, status split (Fork F / NeedsReview) — built inside livrarr-metadata. Carries #97, Bug #2. Land it.
② Modularize (next)Evolve-in-place: extract identity / enrichment / materialize / providers out of livrarr-metadata, leaning on the compiler + WCC's tests. Same logic, mostly a move — like the handlers compile-wall split.
Guardrail: as WCC writes its green code, keep it forward-compatible — don't deepen the identity↔enrichment tangle. The refinements here (provider-key cache, two real state machines, the Materialize crate) are this arc's job, not WCC's.

7 · Open items to resolve when formalizing

Red flags surfaced in the cross-family confer (Gemini) — fold into the spec when this kicks off:

Q2/Q3
Cache keying

Confirm (provider, provider-key), NOT work_id — work_id leaks the Work concept into the provider layer and doesn't exist yet during discovery.

Q4
Provisional write-amplification

Enriching a Provisional work fills an edition that may upgrade to Confirmed — ensure a clean overwrite (no orphaned provenance) on a generation bump.

Q2
Cache TTL / eviction

"Never discard payloads" → DB bloat. Needs a retention policy for stale, unreferenced keys.

Q6
tag_generation

Materialize idempotency: rewrite a file only when merge_generation > tag_generation. Self-healing + retriable. (merge_generation already exists.)
