Livrarr — Metadata Lifecycle & Where the Paths Diverge

Every entry path converges on one spine — WorkService::add / refresh → run_unified_enrichment → EnrichmentService::enrich_work → dispatch_enrichment → merge_impl → apply_enrichment_merge. The paths differ at six forks (A–F) in seed richness, when enrichment runs, which providers run, and how status is classified. Two forks are live bugs (🐞 #1, #2). Sourced from /mnt/opt/livrarr via Serena + code-index, June 2026. Code is the source of truth.

THE ONE IDEA — READ THIS FIRST
One enrichment engine. Six front doors. Every path reconverges on the same spine — they differ only in the seed they start with — its IDs (→ identity) and its metadata (→ content) — and when enrichment runs.  The two bugs are the same shape: a state gets marked “done / terminal” too early, and the deliberately-polite background path can never undo it. Only a manual refresh — which wipes the state — heals them.

The dials, enumerated

An entry point controls three things — and the first two together are the seed: the IDs it carries (→ identity) and the metadata it carries (→ content). They're orthogonal — you can have a strong ID with thin metadata, or vice-versa. The third dial is when enrichment runs. Each is a small, discrete ladder — best at top.

SEED · 1 of 2

🔑 The IDs it carries

Which identifiers the seed hands to WorkService::add. This decides identity — Confirmed vs Pending — not content.

ANCHOR
Work anchor — an OL / GR / HC key. Locks identity → IdentityState::Confirmed. The only ID class that can lock. manual_import.rs:1019 (has_work_anchor)
BRIDGE
Bridge / de-facto ID — ISBN-13 / ASIN. Can't be a federated work anchor, but an ISBN with no resolving ol/gr/hc anchor is the work's Tier-A identity (AC-032) — created resolved (not Pending), upgraded to a work anchor later by the bg resolver (Source 4, REQ-022). manual_import.rs:1019 (has_bridge)
NONE
No ID — title + author only → Pending / pure search; if the resolver can't deterministically match → needs-review (AC-036), not indefinite Pending. manual_import.rs (no-anchor branch)

More anchors don't change the class (still "anchored"); a bridge corroborates an anchor — and when no work anchor resolves, an ISBN serves as the work's Tier-A de-facto identity (AC-032). A GB volumeId never does (ST-002 / REQ-009); a genuinely id-less residue → needs-review (AC-036).

SEED · 2 of 2

📦 The metadata it carries

How much actual field content arrives with the seed. This decides how many providers must run to fill the work.

FULL
Source payload — a complete SourceProviderData block (desc, publisher, genres, pages, rating, cover, series) injected as a synthetic provider. readarr_import_workflow.rs:1226
CACHED
Pre-resolved payloads — full per-provider NormalizedWorkDetails cached at discovery → merged with zero network (≈ a full enrich, free). work_service.rs:2371
PARTIAL
A few fields — title / year / cover_url / description / series carried on the pick or a CSV row. WorkSeedFields (work_service.rs)
FILE
Embedded only — what the file itself carries: ISBN/ASIN/language/title from EPUB dc:* / m4b atoms (also feeds the IDs dial). matching m1_embedded · extract_and_reconcile
NONE
Nothing — title + author only; every field must come from providers. —

Orthogonal to the IDs dial — e.g. List import = strong ID (OL anchor) paired with only PARTIAL metadata.

DIAL 3 · TIMING

⏱ When enrichment runs

Set by the skip_sync flag + presence of source data / cache. Decided in finish_created_work. Earlier = result is ready sooner.

INSTANT
At add, cached — cache hit → merge_from_cached in-process, no provider HTTP; the add returns already Enriched. (Fork A) work_service.rs:2371
SYNC
At add, network — full provider fan-out runs and blocks the response. Triggered when skip_sync=false or source data is present. work_service.rs:2425 → run_unified_enrichment
DEFER
To background — skip_sync=true & no source & no cache → created Unenriched; the 5-min job (Source 2) finishes it. (Fork B) work_service.rs:2425 · jobs/enrichment.rs:12
REFRESH
On demand — user clicks Refresh → wipes retry state, then re-enriches now (Background mode). (Fork C) work_service.rs:1168
SCHED
Every 5 min — recurring recovery, 4 sources: due-retry, stale-unenriched, orphan-failed, identity-pending. jobs/enrichment.rs:12

An entry can hit more than one over time — e.g. Direct Add = INSTANT on a cache hit, else DEFER, then SCHED tidies up.

sync enrichment at add (skip_sync = false) deferred to background (skip_sync = true) rich seed medium seed sparse seed

3 · The six forks — code, pseudocode & why they differ

The six forks aren't six unrelated things — they fall into three kinds. Read them this way and the two bugs stop looking random:

🟢 Speed-only  ·  A, B Decide when enrichment runs — latency only, no correctness risk. Direct Add reuses a cache (A); Add + Manual defer to the background (B).
🔵 Politeness  ·  C, D, E The background path is deliberately lazy so it never re-hammers OL/GR/Audnexus: skip anything already marked terminal (C), defer slow providers (D), merge only safe outcomes (E). Correct by design.
🔴 Traps  ·  F, #2 A state gets marked terminal too early. Because the background path is polite (C/D), it never self-heals — only a manual refresh, which wipes state, recovers it.
💡 Both bugs are the same bug.  Premature “terminal” + a polite background = a permanent stall. Fork F marks a work Unenriched forever (it has a description but no cover); Bug #2 marks Audnexus NotFound forever (the ASIN it needed arrived one pass too late). Both fixes are the same move: let the background path notice the state is stale, not final, and retry it once.
FORK A
Cached-payload reuse (candidate_id round-trip)
When the picked candidate carries a candidate_id, the resolver already fetched + cached the per-provider payloads during discovery. They are re-merged in-process — zero provider HTTP — and this fires even under skip_sync (the gate defers network, not a cache merge).
Code work_service.rs:2371 — finish_created_work → try_reuse_cached_payloads 
let reused_status = match candidate_id {
  Some(id) => self.try_reuse_cached_payloads(user, &work, id).await,
  None => None,   // → fall through to skip_sync / network
};
Why differ
Direct Add from search hits this; manual/list/readarr usually don't carry a resolver cache key, so they go to the network or stay Unenriched.
FORK B
skip_sync gate — enrich now vs defer to background
Interactive Add and bulk Manual Import set skip_sync = true so the slow per-file network fan-out + LLM identity check doesn't block the response. The work is created Unenriched and the background job (Source 2) finishes it.
Code work_service.rs:2425 — finish_created_work, status match 
let enrichment_status = match reused_status {
  Some(s) => s,                                // Fork A won
  None if skip_sync && source_data.is_none()
        => EnrichmentStatus::Unenriched,    // defer ⇒ bg job
  None => self.run_unified_enrichment(..).await, // sync now
};
Why differ
true: work.rs:262 (Add), manual_import.rs (find_or_create).  false: list_service / readarr / author_monitor — they want the work fully enriched before returning. Readarr is exempt anyway (it has source_data, which forces sync).
FORK C
Refresh reset vs background terminal-skip
Same Background mode, opposite retry-state posture. Manual refresh deletes all provider_retry_state rows first, so every provider re-runs. The background job keeps them, so dispatch_enrichment skips any provider whose last outcome is phase-2-terminal (Success/NotFound/PermanentFailure/Conflict/NotConfigured).

  enriched_at=NULL, merge_generation=merge_generation+1 ...
DELETE FROM provider_retry_state WHERE work_id=? ... // keeps provenance
Code — bg skips terminal provider_queue.rs:402 — dispatch_enrichment 
if existing_terminal_outcome(.., provider).await {
  continue;   // is_phase2_terminal() ⇒ never re-queried
}
Why differ
Refresh is a user-driven "try again from scratch"; the bg job must be polite (no re-hammering OL/GR every 5 min). This is exactly why 🐞 #2 needs targeted invalidation, not a blanket reset.
FORK D
Background merge-deferral
In Background mode, if any provider outcome is not merge-safe (and there's no conflict), the queue marks the scatter deferred and enrich_work returns without merging — wait for the slow/retrying provider. Manual/HardRefresh never defer.
Code provider_queue.rs:545 — deferral decision 
let deferred = match mode {
  Background => outcomes.any(|o| !o.can_merge()),
  Manual | HardRefresh => false,   // merge whatever we have
};
Why differ
Background optimizes for eventual completeness; interactive/refresh optimizes for "show me something now". Note: the live work-add/refresh spine always passes Background — Manual/HardRefresh are reached only by the cover service (cover_service.rs:419).
FORK E
Mode-driven merge eligibility
The merge engine decides which providers' payloads are eligible by mode. Background takes only can_merge() outcomes; Manual/HardRefresh take everything except Conflict (e.g. coerces WillRetry/Suppressed in immediately).
Code metadata/src/lib.rs:859 — merge_impl, eligibility filter 
match mode {
  Background => outcome.class.can_merge(),
  Manual | HardRefresh =>
     outcome.class != OutcomeClass::Conflict,
}
Why differ
Pairs with Fork D. Because the live spine is always Background, this branch mostly governs the cover-resolution path today — relevant when unifying modes by entry policy.
FORK F · 🐞 #1
Status classification couples Enriched to a cover
Enriched requires BOTH a description AND a cover. OpenLibrary emits no cover_url in normalized output, so OL-anchored works land description-only → stuck Unenriched → re-picked by bg Source 2 → re-merged every tick (merge_generation climbs ~45), and tag_convergence (which requires Enriched) never writes tags.

6 · Source resilience — the anti-bot access ladder  REQ-032 · REQ-024

Scraped sources (Goodreads) are an eternal cat-and-mouse game — today's working path is no guarantee for tomorrow. The fix is not one magic endpoint; it's to stop treating any single access path as load-bearing. Measured live (June 2026):

Goodreads endpointResultRole
/search?q=…  (HTML)202 AWS-WAF x-amzn-waf-action: challenge — even with a full Chrome header set (header-spoof useless)blocked — needs JS proof-of-work + browser telemetry
/book/show/{id}200 stable HTMLdetail fetch + verification anchor
/book/auto_complete?format=json200 clean JSON: bookId (= gr_key) + workId + title + author + cover; works foreignWAF-free search — current rung 1

The ladder — cheap → resilient · first Hit wins · Blocked escalates

RUNG 1
Structured / JSON endpoint — GR auto_complete. Free, ~10 ms, no HTML-parse, no LLM. Fragile: undocumented; GR can wall it any day.
RUNG 2
TLS-fingerprint fetch of HTML search (wreq / curl-impersonate). Beats passive fingerprinting. Loses to a JS challenge; a maintenance treadmill; needs BoringSSL/cmake.
RUNG 3
LLM with web-retrieval of the walled source (GR — not GB; GB is an open API). Expensive + slow + non-deterministic; gated on a web-capable LLM being configured. Resilient because it outsources the crawl arms race to a provider that can win it (big search/LLM infra crawls the web far deeper than we can). Always verify the returned ID via rung 0.
RUNG 4
Graceful give-up → ISBN-bridge + other providers carry the work; ISBN present → ISBN de-facto identity (AC-032), else → needs-review (AC-036). Degrade, never hard-fail.

Three contracts that let the ladder survive the next move

CONTRACT 1
Rung interface — uniform, cost-ordered
trait DiscoveryRung {
  fn cost(&self) -> Cost;        // orders the ladder
  fn available(&self) -> bool;   // web-LLM configured?
  async fn search(&self, q) -> RungOutcome;
}
enum RungOutcome {
  Hit(Vec<Candidate>), // stop, pass on
  Empty,             // real miss — do NOT escalate
  Blocked,           // WAF/format → next rung + trip breaker
  Unavailable,       // not configured → skip
}
Walk rungs in cost order; first Hit wins; Blocked escalates; Empty is a terminal miss; Unavailable skips.
CONTRACT 2
Detector — classify the response, not the failure
// generalize the existing is_anti_bot_page
fn classify(resp) -> RungOutcome {
  if parsed_candidates(resp).any() { Hit(..) }
  else if challenge_markers(resp)   // 202, waf header
       || content_type_mismatch(resp) // HTML≠JSON
       || empty_body(resp) { Blocked }
  else { Empty }
}
Detect the absence of expected structured data, not one block shape. Tomorrow's wall looks different — key on "no usable signal," not "is it a 202."
CONTRACT 3
Verification anchor — volatile discovery, deterministic identity
let cand = ladder.search(q).await?;     // rung 1..3, fuzzy
let ok = fetch("/book/show/{cand.id}").await?; // rung 0, stable 200
lock_anchor(ok.gr_key);            // never lock an unverified id
An LLM-located (or scraped) ID is a hypothesis; the 200 detail page is the proof. Decoupling flaky discovery from the identity lock is the single biggest resilience move.

🔌 Wire into existing machinery: make the circuit breaker per-(provider, rung) so a blocked rung trips without killing the provider (today it's per-provider) · a Blocked outcome must escalate + WillRetry, never persist as terminal NotFound (that's the premature-terminal bug-class from §3–4) · log per-(provider, rung) success rate so you see the mouse move weeks before users do.
💡 The principle — cat-and-mouse is the steady state: don't fix the endpoint, build the ladder. Degrade, never go dark; verify volatile against stable; outsource the arms race upward when the cheap rungs fail; instrument so you see the next move coming. And keep identity off any single source: when discovery yields no work anchor, ISBN-bridge → else the ISBN itself is the Tier-A de-facto identity (AC-032), upgraded later by the bg Source-4 resolver (REQ-022); a genuinely identifier-less residue → needs-review (AC-036), never a GB volume-id anchor (ST-002 / REQ-009). GB metadata + ISBN keep a work alive even if GR discovery dies entirely.
