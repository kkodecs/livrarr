# Providers & Transport Insights

Outbound HTTP queue, rate limiting/breakers, and per-provider API quirks.

### 22. **Enrichment timeout is 10s per provider**

22. **Enrichment timeout is 10s per provider** (amended from 3s). Hardcover GraphQL regularly takes 2-5s.

### 28. **SABnzbd `search` parameter searches by name, not…**

28. **SABnzbd `search` parameter searches by name, not nzo_id.** See [usenet-pipeline](architecture/usenet-pipeline.md).

### 29. **URL-encode all API keys in query strings**

29. **URL-encode all API keys in query strings.** String concatenation without encoding breaks keys containing `&`, `=`, or spaces. Use `urlencoding::encode()`.

### 30. **All outbound provider HTTP flows through ONE…**

30. **All outbound provider HTTP flows through ONE process-global queue** (`livrarr-http/src/outbound_queue.rs`, Phase 3 metadata-remediation, commits 19af4d5..97963cf). Per-`RateBucket`: pacing (GR 1.5s, OL/HC/GB 1s, Audnexus 2s, Audible 150ms, OL-covers 3s pace-only), in-flight cap 2, priority ordering (Interactive > High > Normal > Low; user search/admin-tests Interactive, Add flow High, monitors/convergence/backfill/list-import Low), and a circuit breaker allowlist (`breaker.rs`): `None`/covers are pace-only (R-5/R-6); the six book-provider buckets each carry one breaker; and `Indexer` is breaker-tracked at TWO levels as of #130 (transport per-origin + rate-limit per-indexer — see insight 71; an earlier version of this insight wrongly said `Indexer` was pace-only). Callers WAIT up to a per-priority reserved depth cap; past it, admission rejects with typed `AdmissionError::QueueFull{retry_after}` → `FetchError::QueueFull` → (alpha-hardening fixes, 2026-07-23) all four provider adapters map it to `ProviderFetchError::QueueFull` → `WillRetry{QueueFull}`, which — like `CircuitOpen` — consumes NO retry budget (audit #6: it previously dead-ended as a terminal error in the adapters). The pre-Phase-3 "token bucket rejects → WillRetry{RateLimit}" pattern is GONE with the enrichment queue's TokenBucket. Breaker-open surfaces as `FetchError::CircuitOpen{retry_after}` → clients map to `WillRetry{CircuitOpen}`, which consumes NO retry budget (`record_will_retry_paused`, R-11 — a pause, never a step toward a terminal dead-end). Breaker signals: `do_fetch` reports transport failures it terminalizes; clients report response-derived Success/Failure/TripImmediately (GR anti-bot body → 1h trip; GB 403 quota body → trip until ~Pacific midnight). The enrichment queue keeps ONLY domain duties: applicability and retry budget. The suppression machinery is GONE (pipeline-hygiene, 2026-07-12, PO-approved after cross-family unanimity): `ProviderOutcome::Suppressed`, `OutcomeClass::Suppressed`, `PermanentFailureReason::SuppressionExhausted`, `record_suppressed`, and the `max_suppressed_passes`/`max_suppression_window_secs` config fields are all deleted — it never had a production producer; migration 073 cleared legacy rows and dropped the `suppressed_passes`/`first_suppressed_at` columns. (Unrelated same-word concepts still live: RSS grab suppression, cross-format decline suppression, identity anchor-conflict suppression, and the identity-completion dead-end "suppression" wording in REQ-008 tests.) **Provider-response honesty (2026-07-27, commits 8bd41d37 + 873f8da4):** a completed 2xx is healthy only once the client reads it as the route's promised application response — every decode/envelope failure files exactly one response-derived breaker `Failure` at the leg that discovers it (`hc_post` is the single GraphQL envelope authority incl. editions and discovery's `lookup_hardcover`; Goodreads autocomplete uses a checked top-level parser; `data`+non-empty-`errors` is rejected, partials never consumed). `BreakerSignal::Success` is singular per operation and owned by the client boundary (`AudibleCatalogClient`/`AudnexusClient`::`fetch`/`fetch_by_asin` terminal healthy arms incl. item-404/410 absences so half-open can close; `GoodreadsClient::fetch` gated on resolution `all_legs_succeeded`) — request helpers never report Success. All four scrape/REST clients are generic over a defaulted `HttpFetcher` (production stays concrete) so real client boundaries are hermetically testable; every request-driving test holds the shared breaker guard. Design: `docs/design-provider-response-honesty.md` (as built).

### 31. **Filter grabs by download_client_id before matching**

31. **Filter grabs by download_client_id before matching.** The download poller must scope grab matching to the specific client being polled. Without this, grabs from one client can be adopted by another.

### 33. **Per-provider error enums, not shared ProviderError**

33. **Per-provider error enums, not shared ProviderError.** Each provider (Hardcover, etc.) has its own error type mapped to `ProviderOutcome` at the call site. Don't create a generic shared error taxonomy prematurely.

### 43. **OpenLibrary author works endpoint structure**

43. **OpenLibrary author works endpoint structure.** The author monitor hits `https://openlibrary.org/authors/{ol_key}/works.json?limit=100`. Response top-level key is `entries` (not `works`, `results`, or `items`). Each entry's `key` field is `/works/OL12345W` — strip `/works/` prefix to get the bare OL work key. `first_publish_date` is unreliable: can be `"2025"`, `"January 1, 2025"`, or other locale-specific formats — parse by finding the first 4-digit numeric token (`.split(!is_ascii_digit()).find(|tok| tok.len() == 4)`). No auth. Rate bucket: `RateBucket::OpenLibrary`. Timeout: 30s.

### 45. **OL anti-pattern**

45. **OL anti-pattern: hundreds of `/works/{key}.json` round-trips.** OL explicitly names this as a bad-citizen pattern. Use `search.json?q=...&fields=...` for batch retrieval whenever the alternative is N single-record fetches. Bulk operations (>1k records) should not hit the API at all — use the monthly data dumps (TSV+JSON, available via torrent) and the RecentChanges API for freshness deltas. The full OL operational guide is at [`wiki/integrations/openlibrary.md`](integrations/openlibrary.md).

### 58. **Process-global breaker state wedges parallel tests**

58. **Process-global breaker state wedges parallel tests — mechanism proven, fixed in `livrarr-external-data`, still open in `livrarr-enrichment` (2026-07-26).** `outbound_queue::shared()` is a `OnceLock` singleton (insight 30), so each test binary's per-provider breakers are ONE piece of mutable state shared by every test in it. A test that deliberately trips a breaker and does not reset it leaves that provider Open for the production duration — **3600s for Goodreads** — and every later test in that binary is refused admission before a socket is opened. Resetting at the END of the tripping test is NOT enough: a sibling scheduled inside that window still observes the open breaker. **The symptom is a hang, not a red test** — a test awaiting its own one-shot server waits forever for a connection its client never attempts (`strace`: `socket`/`bind`/`listen`, no `connect`). It stayed hidden because the Goodreads client used to report `BreakerSignal::Success` on any non-anti-bot 2xx, and `record_success` clears failures AND closes an open breaker, so unrelated passing tests were accidentally cleaning up; removing that premature success (correct on its own merits — a bare 200 does not prove a readable page) made the latent defect reliable. **Do not restore it to make tests pass.** Fix pattern, applied in `livrarr-external-data/src/test_support.rs`: ONE breaker mutex per binary, PRIVATE, reachable only via `lock_gr_breaker() -> GrBreakerGuard`, which resets to production defaults on guard entry AND on drop (drop-guard, so a panicking test cannot leak an Open breaker or a one-strike config); every test that emits a breaker signal, reads breaker state, **or merely drives a real fetcher at that bucket** takes it; and any test standing up a one-shot server bounds its wait with `tokio::time::timeout`. Two same-named locks in different modules serialize NOTHING — that mistake was made here first. **Still open:** `provider_queue_tracer_tests::goodreads_tracer_tests::goodreads_through_queue_returns_success_for_direct_gr_key_lookup` in `livrarr-enrichment` (characterized flake since 2026-07-02, `WillRetry{CircuitOpen}` ~1 in 8 full runs) has the identical shape — its sibling anti-bot test at `provider_queue_tracer_tests.rs:320-365` trips the shared breaker and resets only after asserting, neither holds a lock. `test_support` is `#[cfg(test)]`-private to external-data, so enrichment needs its own guard or the guard moves to `livrarr-http` behind `test-helpers`. Until then, on a full-suite failure of ONLY that test, re-run once. Full write-up: `~/Projects/kk-build/wiki/livrarr/test-suite-shared-breaker.md`. **SWEEP COMPLETE in `livrarr-external-data` 2026-07-26:** the guard's real API is `lock_breaker(bucket) -> BreakerGuard` (one process-wide mutex for ALL buckets, not one per bucket — the queue's pacing and in-flight caps are shared too); `lock_gr_breaker()` is the Goodreads convenience wrapper. 81 further request-driving tests across `openlibrary.rs`, `google_books.rs`, `hardcover.rs`, `audnexus.rs`, `goodreads/client.rs` and `provider_client.rs` now take it — the criterion is **drives a provider request function**, not "emits a signal on the branch this test happens to take", because branch-by-branch reasoning is exactly what leaves the next latent one behind. Serializing them costs nothing measurable (the binary is pacing-bound: 221→222 tests, 12.02s, identical across five runs). Two things the sweep unblocked: an absence-of-signal assertion is only writable once EVERY emitter in the binary holds the lock (Audible's "a 404 from the by-ASIN item lookup must not trip" had to be written as a comment until it landed), and it surfaced a missed production site — `audnexus.rs`'s `cached_fetch` served both an ITEM route and a SEARCH route through one 404/410 absence exemption, so a dead Audnexus search route read as "book absent" with the provider still green (fixed with an `Absence` route-kind parameter; red-first proven).

### 62. **Provider parsers must distinguish "unreadable" from…**

62. **Provider parsers must distinguish "unreadable" from "empty" and WARN — never degrade silently; an empty parse is DRIFT, not truth (N1, 2026-07-03).** Three GR parse paths drifted silent-empty in one day (autocomplete rating type, series-page React redesign, cover desync) — reviews cannot catch this class, only live behavior can. Standing discipline: parse list entries INDIVIDUALLY (one rogue entry drops alone, warn-logged); warn on unreadable-body/shape-drift; never persist emptiness over stored data. GR series pages (2026-07 React layout): books ride in `data-react-props` JSON blobs, primaries FIRST with the header's "N primary works" as the roster cutoff — blob membership includes omnibuses/splits/translations (43318 lists 27 entries for 3 primaries), so membership ≠ primary set; positions exist ONLY in title decorations "(Series, #N)" and are trusted only when the decoration names the page's own series (umbrella pages never borrow sub-series numbers); pagination is the `numWorks/currentPageNumber/perPage` counter blob (numWorks = TOTAL works). Roster hardening: stored-empty reads as absent (heals on open), a shortfall vs the declared primary count refuses a partial roster, the monitor never writes an empty fetch, and every roster save pairs with a `work_count` update (ST-007: count IS roster size). Real captured pages: `crates/livrarr-external-data/fixtures/gr-series-{108562,43318}.html`.

### 68. **Persistent provider-response cache**

68. **Persistent provider-response cache: ONE table, ONE seam, policy at the seam (U-B1, 2026-07-12).** `provider_response_cache` (migration 072; global, deliberately no user_id) keys successful detail payloads by (provider, anchor_type, anchor) — anchor_type strings `isbn13|gr_key|hc_key|ol_key|asin` derived from the dispatched `AnchorQuery` variant. The ONLY consult/write point is inside `DefaultProviderQueue::dispatch_enrichment` (`livrarr-enrichment/src/provider_queue.rs`), after applicability → anchor derivation → terminal-skip; `ProviderResponseCacheDb` (livrarr-db) is storage-only — TTL comparison, success-only writes, and the `Freshness` knob live at the seam, never in the DB layer and never at call sites (insight 56's chokepoint rule). `EnrichmentContext.freshness` carries the knob: user refresh (`RefreshSurface::Interactive` AND `Bulk`) = `Bypass` (always fetches, rewrites the row); add/re-add, convergence, monitors, list import = `PreferCache` (fresh row ⇒ zero HTTP; payload rides into budget rules/persistence/merge exactly like a fetched Success). Freshness is orthogonal to `RequestPriority` (D-004). Success-only: errors/not-found are NEVER cached (a NotFound provider re-fetches next pass, still governed by the retry/terminal budget). `fetched_at` stamps at write time; eviction is oldest-first (`fetched_at, rowid` tiebreak) down to `max_rows` after write batches. Config `[metadata_cache] ttl_days=7 / max_rows=100_000`, TOML only. A cache hit emits NO provider call record (records instrument real HTTP at the client wrapper — never invoked on a hit), so call-record-based stats/evidence stay truthful; measured live: warm re-add = zero provider HTTP (baseline doc §6). **Test-fixture trap that bit this suite:** `reset_enrichment_for_refresh` only flips `works.enrichment_status` — it does NOT clear `provider_retry_state`, and both Success and NotFound are phase2-terminal, so a second same-work pass terminal-skips before the cache unless `reset_all_retry_states` (or `reset_for_manual_refresh`) is also called.

### 69. **HTTP clients are consolidated shared instances**

69. **HTTP clients are consolidated shared instances; bulk refresh is bounded-concurrent (U-B4/U-B5, 2026-07-12).** main.rs builds exactly FOUR shared HTTP surfaces: `http_client` (unrestricted, 30s+UA), `http_client_safe` (SSRF-safe, 30s+UA), `http_fetcher` (the ONE `HttpFetcherImpl` — every service construction clones it), and `llm_http_client` (unrestricted trust class — LLM endpoints are admin-configured infra per insight 37 — 60s timeout + UA; replaced three bare no-timeout/no-UA builders that could hang unboundedly). New wiring must CLONE these, never construct fresh instances (reqwest clients share their pool on clone; all fetchers already share the process-global outbound queue, so consolidation changed no provider-facing behavior — measured: `docs/connection-reuse-report-2026-07-12.md`, 24 requests → 1 connection per provider host, verdict = keepalive tuning permanently skipped). `refresh_all`'s sweep body is the free fn `bulk_refresh_sweep` (`livrarr-handlers/src/work.rs`): `buffer_unordered(3)`, per-work failure isolation, Bulk surface — pinned by `test_responsiveness_bulk` (bound + exactly-once + counts) and the concurrent-Retry serialization pin in `test_responsiveness_add` (KeyedMutex queues, never rejects). Ops note: `init_tracing` honors `RUST_LOG` when set (replaces the config filter wholesale — the only way to enable non-livrarr targets like reqwest connect tracing); unset = config-derived filter exactly as before. **Measured 2026-07-12: N=3 bulk refresh delivers NO wall-clock win** (2.0 s/work before AND after, 178-work sweep ~6 min) — the sweep is pacing-bound on the shared provider buckets (ST-012's worst case: per-work enrich stretches ~3× under contention, total throughput = bucket throughput). Do NOT reach for more work-level concurrency to speed Refresh All; and do NOT resurrect Hardcover batching for it either — **HC batching (REQ-010) was CANCELLED by the PO 2026-07-12** (documented reason: "Claude was wrong. This is NOT worth it. Gemini and Codex are unanimous in their judgement. This was a goose chase.") because the sweep wall belongs to the Goodreads/Audnexus buckets (161×1.5s / 134×2s on the live library) and the U-B1 cache already zeroes repeat HC fetches; full trail in spec REQ-010 + design §4.2 (baseline doc §7).

### 70. **ONE qBittorrent state classifier (quality-waves 2a…**

70. **ONE qBittorrent state classifier (quality-waves 2a, 2026-07-13).** `classify_qbit_state` (`crates/livrarr-download/src/lib.rs`) maps every qBit state string to BOTH projections at once — `QbitStateClassification { ui_status: QueueStatus, import_safe: bool }` — per the ratified table in `docs/d1-qbit-state-truth-table-2026-07-13.md`. ### 71. **Indexer citizenship**

71. **Indexer citizenship: origin-keyed buckets, breaker cooldown, live search cache (indexer-citizenship unit, 2026-07-14; contract = `design-indexer-rate-limits.md`, 4-round design review + r6/r7 code reviews).** Every indexer-origin fetch — search, RSS, grab-time torrent/NZB downloads, the magnet-redirect probe — rides `RateBucket::Indexer(<origin>)` where origin = `livrarr_http::normalized_origin(url)` (lowercased `scheme://host[:port]`, default port omitted; ONE authority, in livrarr-http because domain lacks the `url` dep). The bucket key is the CONFIGURED indexer's origin (grab resolves it by display name via list_indexers, falls back to the download-url origin) so same-host indexers share one lane and one cooldown. Indexer buckets are breaker-tracked; a 429 sends TripImmediately with a 30-min cooldown (indexer buckets only — book-provider 429 signals unchanged); callers surface CircuitOpen as a per-indexer warning and skip until cooldown. A RateLimited/CircuitOpen torrent-file fetch FAILS the grab — never falls back to handing the indexer URL to qBittorrent (that would bypass pacing by delegation); other failure kinds keep the URL fallback. Download-client RPC (qBit auth/add, Transmission RPC, SAB POST) is deliberately `RateBucket::None` — classify fetch sites by URL PROVENANCE, never by file location. Search cache: `ReleaseSearchCache` in livrarr-download (key (title, author, indexer_id), 24h TTL) — `cache_only` = zero HTTP with all-miss = successful EMPTY (AllIndexersFailed reserved for live modes); default = per-indexer cached-if-fresh with write-back; `refresh` = always live. The Releases tab mounts cache-only (`modeRef` init "cacheCheck"); the Search button forces live. `HttpFetcher::fetch_no_redirect`'s DEFAULT follows redirects (only HttpFetcherImpl truly suppresses) — test doubles must override both. Pins: `crates/livrarr-download/tests/indexer_citizenship_pins.rs` (7) + `crates/livrarr-http/tests/indexer_breaker_pins.rs` (1) — package-local tests/ dirs are gitignored: new files there need `git add -f`. **#130 RESOLVED — two-level breaker (2026-07-21; contract `docs/design-issue-130-per-indexer-breaker.md` r3, both-family design PASS).** The single origin-keyed breaker blacked out EVERY indexer behind one Prowlarr host on any one indexer's 429 (Prowlarr stores each indexer as `{base}/{id}`, so all normalize to one origin → one shared breaker). Fix: `RateBucket::Indexer(String)` → `Indexer { origin, indexer: Option<String> }` with TWO disjoint breaker levels. TRANSPORT breaker per `origin` (pace-key; `BucketHandle.breaker`; trips on connection/timeout at 5/60s; NEVER sees a 429; shared across the host — restores dead-host protection for the search fan-out). RATE-LIMIT breaker per configured-indexer `id` (`OutboundQueue::rate_limit_breakers`, keyed by the FULL bucket value; a 429 → `TripImmediately`, open = `Retry-After` delta-seconds clamped [10s,6h] else 30-min default; `indexer:None` fallback has none). `do_fetch` owns indexer signal routing: 429 on `indexer:Some` → rate-limit trip + transport SUCCESS (host answered, must not look dead to siblings); 429 on `indexer:None` → transport success only; any completed non-429 response → transport + rate-limit success (closes a half-open). `pace_key()` erases the id for the pace registry; `run_dispatcher` gates a grant on BOTH breakers under a single Phase-1 lock hold (early-drain, no rl-breaker TOCTOU) plus a Phase-3 grant-time re-check (catches a trip during the pacing sleep / a priority reorder). All 6 call sites thread `indexer.id.to_string()`; `indexer:None` only when a grab's indexer name no longer resolves (pace + transport gate still apply). `report_outcome` stays the TRANSPORT reporter (providers unchanged); `report_rate_limit_outcome` is the new per-indexer reporter. Pins: 8 two-level unit tests in `outbound_queue.rs`, Retry-After matrix in `fetcher.rs`, and `indexer_breaker_pins.rs` rewritten to the same-origin-siblings #130 e2e.

### 79. **The process-global outbound queue can wedge**

79. **The process-global outbound queue can wedge: a dispatcher dies with the runtime that spawned it, and every caller already parked in `acquire` waits forever (identity-edit contest, 2026-07-24/25).** `DispatcherGuard` clears `dispatcher_running` when a dispatcher dies, but that only helps the NEXT arrival — items already in the heap starve if every remaining caller is already blocked on its turn. This is exactly what happens when several `#[tokio::test]` runtimes share the one process-global queue (insight 30/58's global-state pain). **Strength of evidence: THREE of the four independent contest implementations, with no knowledge of each other, added the same fix to `crates/livrarr-http/src/outbound_queue.rs`** — a periodic re-check in the `acquire` wait that respawns the dispatcher when `!dispatcher_running && !heap.is_empty()` (codex 100ms, opus 250ms, fable; CC alone did not, and CC's gated suite is the only one that hangs under default test parallelism — killed at 7min where the others finish in ~37s). Isolated by experiment: applying codex's diff to the CC tree turned a 7-minute hang into a 36.82s completion, single variable, under heavier load than the control. In production one runtime owns the process, so the watchdog never fires — the wedge is a test-environment manifestation of a real latent hole in shared infra. **Do not read "only CC hangs" as "CC's bug"** — the hole is in `livrarr-http`; CC's provider-call pattern is merely the one that trips it. Whichever entry merges, the queue fix should ride along. **RESOLVED 2026-07-25: fable merged, and its tree carries the watchdog (+47/-12), so it did ride along. Whether to KEEP it is still an open PO call — it is a `livrarr-http` change, not an identity-edit one.**
