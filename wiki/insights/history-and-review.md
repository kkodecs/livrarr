# Work History, Identity Review & Cutover Insights

The work-history event log, the identity-review card surface, and the F2 identity-layer cutover ceremony.

### 77. **Work history is complete and single-authority…**

77. **Work history is complete and single-authority (work-history feature, 2026-07-20, `aa7f6985`).** 14 event kinds, every lifecycle moment writes exactly one event at its moment of truth. **Payloads:** built ONLY via the typed constructors in `livrarr-domain/src/history_events.rs` — never ad-hoc `json!` at a writer site; work-attached payloads carry `work_title` (+`work_author` where sensible) so rows stay identifiable after `history.work_id` nulls on work delete; grab-family `title` means the RELEASE title, never the work's. **Write paths:** `record_history` (livrarr-db; infallible observer — warns, never propagates, REQ-009) for in-crate writers; the domain `HistoryService::record` trait method for the four compile-walled handler doors (identity review-apply, pending-anchor affirm, manual-import confirm loop at import_single_item's sole caller, root-folder adopt). **Moments:** birth = one `added` at `finish_created_work_fast` entry (the sole `created:true` constructor; the source door label is stamped inside the six `seed_*` constructors via `WorkCandidate.add_source` — a caller cannot mislabel); enrichment = exactly one of `enriched{changed,status,tags_written}`/`enrichmentFailed`/nothing per `run_unified_enrichment` invocation, nothing ⟺ `merge_deferred` ∨ `!attempted` (`EnrichmentResult.attempted` is authored by `enrich_work`'s own control flow — the cached-reuse arm completes with an EMPTY outcomes map, so outcome-emptiness is NOT a no-attempt signal; `changed` = the `content_changed` row diff, insight 76); tag events = one per work per pass inside `retag_library_items` (covers all three callers) + per-item `tagWritten` on convergence-recovery success + NO separate event for materialize's in-enrichment write (it rides `enriched.tags_written` — one moment, one event); deletes = `fileDeleted` per user file door, `workDeleted` composite with `work_id` NULL written AFTER successful deletion (D-DELETE-ORDER — before-delete risks false events, after-delete can't carry the FK), Readarr undo emits per-file + per-orphan events `undo:true`; `merge_works` repoints loser history to the survivor inside the merge tx (the old "cascades away" comment was WRONG — ON DELETE SET NULL orphaned them) + one `worksMerged` on the survivor; `identityResolved` fires on the four USER identity doors only (review dismiss and system-side anchor writes deliberately excluded). **SAB failure arm:** `downloadFailed` writes ONLY after `update_grab_status` returns Ok — on a failed update the grab stays active and the poller re-enters the arm next tick, so an early write duplicates (code-review r1). **Robust reads:** an unrecognized stored `event_type` is skipped-with-warn in both list methods (rollback safety); the paginated COUNT stays raw — documented accepted drift (D-COUNT), do not "fix" it. **Backfill** (`crates/livrarr-server/src/jobs/history_backfill.rs`, 4th startup pass): one-time (marker `history_backfill_generation` in `_livrarr_meta`, written via INSERT..ON CONFLICT — the key is unseeded, a bare UPDATE silently no-ops), synthesizes added/last-enriched/grabbed/imported + grab-failure events from persisted timestamps only, every row `backfilled:true` with the FACT date; per-fact dedup: grabbed by payload `guid`; failures TWO-TIER (a guid-carrying row — backfill-written — covers exactly its grab; a guid-less row — live writers — covers by (work_id, release title)); imported covered by a same-work Imported/ImportFailed row dated within [imported_at−5s, +1h] inclusive; grabbed/failure synthesis ONLY for Imported/Failed/ImportFailed grabs — Sent/Confirmed/Importing/Removed synthesize NOTHING at all; inserts are fallible per-row, any failure skips the marker and the next boot's rerun is additive; `DELETE FROM history` is P0-forbidden everywhere including idempotency. First live run: 6 → 420 rows, every count reconciled exactly (143 added / 142 enriched / 129+3 imported / 3 grabbed all pre-covered). **Frontend:** the `EventType` TS union drives three compiler-forced Record maps in HistoryPage; the runtime `??` fallbacks ARE the version-skew rendering — load-bearing, never remove; deleted works render `data.work_title` before "—".

### 86. **When one workflow reads resource A and records…**

86. **When one workflow reads resource A and records approval state in resource B, shared-handle tests cannot prove ownership (identity cutover ceremony, 2026-08-10).** Cutover Rehearse correctly derived report content from a copied snapshot but accidentally persisted `identity_cutover_runs` and `identity_cutover_reports` through the snapshot-backed `SqliteDb`; Apply reopened the live data-dir DB and rejected an identical approved fingerprint because the ledger row was elsewhere. Unit/behavioral tests stayed green because they drove Rehearse and Apply through one shared handle, collapsing source and ledger into the same resource. The durable pattern is explicit ownership at the write call (`build_migration_report(snapshot_db)`, `persist_cutover_report(live_db, ...)`) plus a regression that launches the production CLI as separate processes and inspects both databases. Apply this to any split-pool, cache/source, staging/live, or snapshot/ledger seam.

### 87. **A migration report is an executable approval contract…**

87. **A migration report is an executable approval contract, and persisted discriminators need one explicit codec (identity cutover ceremony, 2026-08-10).** Rehearse counted duplicate full-identity cohorts, but Apply independently inserted one GroupIdentity card per Work; on the real library that turned one approved cohort into 146 pending cards. Derive report counts and staged artifacts from the same deterministic cohort helper, then compare every staged category count to the approved tuple inside the staging transaction before commit. Separately, never use `serde_json::to_string` for a plain SQL TEXT discriminator: it stores JSON quotes. `ReviewKind::{storage_code,from_storage_code}` is now the sole `identity_review_cards.kind` vocabulary across writers, filters, repository reads, and the CLI. A binding regression needs N records with exactly one flagged cohort, exact report-to-row cardinality, raw-code inspection, and a round trip through the real operator command.

### 88. **Nonempty is not a cutover blocker**

88. **Nonempty is not a cutover blocker; only failed staged invariants are (identity cutover ceremony bug #4, 2026-08-10).** `index_ready = legacy_work_count == 0` made every real library permanently Blocked with zero cards, while all empty-fixture readiness tests stayed green. Readiness must dry-run the exact tuple enforced by `idx_works_identity_v2` — `(user_id, normalized_identity_main, normalized_identity_subtitle, normalized_identity_volume, primary_author_id, text_distinction)` — over the same projection Apply persists. Zero collision cohorts means Ready even when Works exist; every collision cohort means one resolvable `GroupIdentity` card. A binding ceremony needs both halves: a nonempty clean fixture that reaches Ready and crosses the startup-readiness marker/index transaction, and a collision fixture that is Blocked with its exact card, resolves through the real CLI, and reaches Ready on rerun. Never allow a persisted Blocked state with no operator-resolvable artifact.

### 89. **A migration writer, migration report, and startup…**

89. **A migration writer, migration report, and startup version guard are one compatibility contract (identity cutover ceremony bug #5, 2026-08-10).** Migrations 082/083 wrote `_livrarr_meta.schema_version=83` and `build_migration_report` required 83, but `MAX_SCHEMA_VERSION` remained 38; consequently the binary rejected every database it had just migrated. DB-level readiness tests all passed because they never drove the preceding compatibility gate. Keep one shared DDL-version key unless the IR explicitly defines separate version domains, set the binary maximum to the highest schema it writes, and retain `>` rejection for genuinely newer databases. A cutover ceremony is incomplete until its exact nonempty Apply database crosses the full post-migration production boot seam in runtime order: version gate, then authority readiness.

### 91. **A review card's mint generation is history**

91. **A review card's mint generation is history; the actionable CAS generation is the one shown when the user decides (PACKET-FIX-STALECARD, 2026-08-11).** GroupIdentity cards can remain pending while enrichment, heals, or other legitimate settlements advance the anchor Work. Listing/loading such a card must refresh its response generation from the current anchor without rewriting the stored mint record. Resolve then rechecks that claimed generation and the underlying proposal inside the transaction: every proposed Work must still exist, and each route snapshotted when a new merge card was minted must still resolve into the proposed cohort. Mere generation drift proceeds; proposal invalidation returns a specific 409, writes nothing, and leaves the card dismissable. This is insight 80's decision-time observation rule applied to delayed human continuations.
