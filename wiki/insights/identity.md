### 80. **Identity edits are protected by a generation stamp…**

80. **Identity edits are protected by a generation stamp, and the guard is only as good as the writer that honours it (identity-edit merged 2026-07-25, `a7f03540`).** `works.identity_generation` (migration `076_anchor_uniqueness_identity_generation.sql:12`) is the coordination primitive for every identity writer. The protocol is: read `(Work, identity_generation)` in ONE transaction **before** provider I/O, then submit exactly one claimed `complete_anchors(work_id, expected_generation, completion)` **after** it; a lost claim returns `IdentityCompletionOutcome::Superseded` and writes **nothing**. The canonical implementation is `crates/livrarr-identity/src/async_resolver.rs:132` (pre-await read) and `:259` (claimed completion); all six resolver roads funnel through it. `tests/behavioral/test_identity_edit_race_repro.rs` pins the refresh road — real refresh, real HTTP clear door, resolver parked via `StubProviderClient::with_delay`, proceeding on `call_count() > 0` and never a timer.

    **The trap, and it is the whole lesson:** the CAS is easy to have and easy to render useless. Two ways, both live in the tree today. (a) **Never claiming** — the post-await write calls the legacy unguarded repository method (`merge_missing_anchors`, `set_identity_confirmed`). That is what the losing contest entries did, and the race repro catches it. (b) **Claiming a generation observed too late** — `complete_add`'s delayed-NotFound arm (`crates/livrarr-metadata/src/work_service.rs:1192-1197`) reads `(work, generation)` *after* enrichment already returned, so it faithfully claims a generation its decision never saw and stamps a stale conclusion over the user's edit. Form (b) passes every "is there a CAS?" review and is invisible to the race repro. **The question to ask a writer is never "does it claim?" but "was the claimed generation observed at the moment the decision was made?"** Convergence's Pending→NeedsReview arm (`crates/livrarr-metadata/src/convergence_service.rs:50` read, `:92-96` unconditional write) and add/adopt preflight (`crates/livrarr-metadata/src/work_service.rs:288-310`, three separate transactions, no generation at all) are the other two writers still outside the protocol. All tracked in `docs/design-identity-edit-fixes.md`.

    Also load-bearing: `work_identity_anchors` carries its own `user_id` (same migration, `:6`). Ownership questions must be answered by querying that table directly — the merged backfill (`crates/livrarr-db/src/sqlite_work_identity.rs:2132-2163`) instead builds an owner map from works that have a non-NULL legacy column, so a work owning a confirmed ledger row with all five columns NULL is invisible, a second owner gets inserted, and the `uniq_user_confirmed_work_anchor` index **fails startup**. `race/cc`'s `work_identity_ledger_backfill.rs:222-224` shows the direct-ledger form.

**Amended 2026-08-31 (deletion pass):** the retired legacy writers this note worried about (`set_identity_status`, `set_identity_pending`, `set_needs_review`, `dismiss_review`, `merge_missing_anchors`, `record_pending_anchor`, `confirm_anchor_and_recompute_badge`, the dead-end trio) are deleted from the repository trait — there are fewer writers left to honour the stamp, and every remaining one is live.
