# Spec: work-history

## 0a. Design Principles

- **Record facts, never fabricate them.** A history event is written at the moment the thing happens, by the code that did it. The backfill (REQ-010) synthesizes events only from facts that persist with real timestamps, and every synthesized row is explicitly marked. No invented dates, no guessed sources.
- **History is an observer, never an actor.** Writing a history event must never change, delay, or fail the operation it records (REQ-009). If the event write fails, the operation still succeeds.
- **One moment, one event.** Each lifecycle moment produces exactly one event regardless of which trigger caused it (add vs refresh vs background job). Composite operations record the composite, not the parts (deleting a work = one `workDeleted`, not N `fileDeleted` + one `workDeleted`).
- **Local-only data.** History rows never leave the machine (existing privacy invariant), so file paths and release names in event payloads are acceptable.
- **Uncertainty is visible** (product principle): user identity decisions are part of a work's story and deserve a record.

## 1. Problem Statement

The work page has always had a History tab, and the app has a global Activity → History page, but they are nearly empty: of ten defined event kinds, only three are ever written (grabs, SABnzbd download failures, and downloaded-file imports). The most common things that happen to a book — being added, getting metadata, having tags written into its file, being deleted or merged — leave no trace. Manual imports log nothing at all (the code intended to do it is dead). Merging duplicates silently orphans the merged-away work's history.

The result: the user cannot answer "what happened to this book?" or "what did the app do last night?" — even though the storage, API, and UI for answering it already exist.

This feature makes history complete: every meaningful moment in a work's life writes an event, two latent history bugs are fixed, and a one-time backfill reconstructs the honestly-knowable past for existing libraries.

## 2. Requirements

**New event kinds** (stored as text; kinds: `added`, `workDeleted`, `worksMerged`, `identityResolved`): **REQ-001, REQ-006, REQ-007, REQ-008**. Existing unused kinds get writers: `enriched`, `enrichmentFailed`, `tagWritten`, `tagWriteFailed`, `fileDeleted` (REQ-002, REQ-004, REQ-005). Existing kinds `imported`/`importFailed` gain the missing manual-import writer (REQ-003).

- **REQ-001** — Birth event. When a work is newly created — by any road: interactive add, list import, Readarr import, author monitor, series monitor, or file-scan import — exactly one `added` event is recorded for that work, carrying the work title and the source door (`search` | `list-import` | `readarr` | `author-monitor` | `series-monitor` | `file-import`). Returning an already-existing work (dedup/re-add) records nothing. How the source door reaches the shared creation road (a candidate field vs a call parameter) is a design-stage decision; the requirement is only that the recorded door is the true one.
- **REQ-002** — Metadata events. Every enrichment attempt that completes — regardless of trigger (add, manual refresh, bulk refresh, background convergence, monitors) — records exactly one event: `enriched` when it applies (payload: whether any field changed, and the resulting status incl. settled-but-sparse), `enrichmentFailed` when it fails (payload: reason summary). An attempt that never runs (blocked by identity state, terminal-skipped) records nothing. A background attempt that completes WITHOUT concluding — the deferred-merge outcome, where dispatch runs but the merge is skipped (`enrich_work` returns `merge_deferred: true`, `livrarr-enrichment/src/lib.rs:620-641`) — also records nothing: the later attempt that actually merges (or terminally fails) is the recorded moment (round 4).
- **REQ-003** — Manual-import parity. A file imported or adopted through the manual-import road records `imported` (or `importFailed`). Payload note: the existing download-import road records batch counts (`title`, `imported`/`failed`/`skipped` counts — `import_workflow.rs:1300-1305`); the manual road records per-file detail (work title, path, media type). Both shapes are valid `imported` payloads and both history surfaces must render both (REQ-011). The dead `ManualImportService::create_history_event` method is either wired or removed — not left as a false affordance.
- **REQ-004** — Tag events. Every tag-write pass for a work records one event per work per pass: `tagWritten` (payload: files attempted/succeeded) or `tagWriteFailed` when zero files succeeded (payload: first error). Coverage across the THREE tag-write paths (ST-006): the batch retag road (import-time, post-enrichment, cover-swap) records one event per work per pass; the convergence sweep's per-item recovery — which iterates items globally, not by work — records one event per recovered ITEM with a single-file payload (round 3); materialize's in-enrichment tag write records NO separate tag event — it is part of the enrichment moment, and that moment's `enriched` event payload carries a `tags_written` flag instead (round 4; "one moment, one event"). Whether the paths later unify is a design-stage decision — the behavior is: no tag write to a library file goes unrecorded, either by a tag event or by the enclosing enrichment event's flag.
- **REQ-005** — File deletion. Every user-initiated library-file removal records `fileDeleted` (payload: path, media type, work-title snapshot). The file-removal doors, enumerated and classified (review round 2, Codex): (a) the library file-delete road (`livrarr-library/src/file_service.rs` ~:61) — `fileDeleted`; (b) the manual-import file delete (`manual_import_service.rs:70-76`) — `fileDeleted`; (c) the secondary-API delete (`api_secondary_impl.rs:692-704`) — `fileDeleted`; (d) whole-work deletion (`work_service.rs:1508-1519`) — the `workDeleted` composite only (REQ-006), no per-file events; (e) Readarr import UNDO (`crates/livrarr-server/src/readarr_import_workflow.rs:297-345`) — records `fileDeleted` per removed file and `workDeleted` per removed orphan work, each payload marked as import-undo (note: undo's orphan-work removal bypasses the work-delete service today, so it needs its own writes); (f) import-internal replace cleanup (`import_workflow.rs:281`) — out of scope, part of the import moment. No other production file-removal road exists (call-site enumeration 2026-07-18).
- **REQ-006** — Work deletion. Deleting a work records one `workDeleted` event (payload: title, author, count of files removed) — not per-file events. The event and the work's prior history rows survive the deletion (ST-001) and remain visible in the global history page. Constraint note (review round 2): the history FK means the event row must be written so its insert succeeds — either before the work row's delete (the deletion then nulls its reference) or with a null reference outright; either way it ends unattached, identified by its payload (REQ-013).
- **REQ-007** — Merge repoint + event. Merging a duplicate into a survivor (a) repoints the merged-away work's history rows to the survivor inside the same transaction that moves its files and grabs (closing the ST-002 orphaning bug), and (b) records one `worksMerged` event on the survivor (payload: merged-away title + id).
- **REQ-008** — Identity decisions. Each explicit user identity decision records exactly one `identityResolved` event (payload: which action, and the chosen identity in human-readable form). The covered doors, enumerated (review round 1, Codex): (a) applying a review candidate to a review-parked work; (b) resolving an identity conflict with ANY of the four actions — `KeepExisting`, `AcceptSeparate`, `ReplaceAnchor`, `Merge` (`livrarr-domain/src/identity.rs:515-518`) — a kept-existing identity is still a user decision and is logged with its action; (c) affirming a pending anchor guess; (d) a manual user identity edit that confirms or supersedes an anchor (the user-initiated callers of `confirm_anchor`/`confirm_anchor_and_recompute_badge`/`supersede_anchor`, `livrarr-domain/src/services/work_identity.rs:31-59`). System-initiated anchor writes (import, resolver, convergence) do NOT log this event. Dismissing a review (which defers, settling nothing) does not log it (see Non-Requirements).
- **REQ-009** — Observer, never actor. A failed history write never fails, blocks, or retries the operation that attempted it; it logs a warning. No history write occurs for an operation that did not happen.
- **REQ-010** — Backfill. A one-time startup pass synthesizes history for existing libraries, from persisted facts only (ST-007). Its rules, each binding:
  - **What is synthesized:** `added` from each work's add date (source omitted); `grabbed` from each surviving grab (title, indexer); `imported` from each file's import date; at most one `enriched` from each work's last-enrichment timestamp; grab-failure events with the explicit status mapping `GrabStatus::Failed` → `downloadFailed` and `GrabStatus::ImportFailed` → `importFailed` (`import_error` text in the payload; `Removed` and in-flight statuses synthesize nothing), dated at the grab date — the only persisted timestamp.
  - **Marking:** every synthesized row carries `backfilled: true` in its payload (plus the REQ-013 `work_title` snapshot).
  - **Dedup is per source fact, not per event kind** (round 1): each individual fact (a grab, a file, a work) is synthesized unless an existing row — live or backfilled — already covers THAT fact. Real `grabbed` payloads carry the release `guid` (`release_service.rs:467-472`) matching `grabs.guid`, so grab matching is exact.
  - **Imported coverage rule, fixed here** (rounds 2–4): real grab-road `imported` events carry only batch counts — no file identity — and `library_items` do not link back to grabs, so per-file matching cannot be exact. An existing real `imported`/`importFailed` event COVERS a library item iff it is for the same work AND its date falls in `[item.imported_at − 5s, item.imported_at + 1h]`. Items with no covering event are synthesized. This makes imported-file backfill explicitly BEST-EFFORT: completeness is traded for never duplicating a batch-covered file, and the one loss case — a manual import of the same work landing inside that window of a grab import's completion — is a declared, accepted false negative, not an oversight. Fixtures must pin both sides of the window.
  - **Idempotency is non-destructive** (round 3): a crash mid-pass followed by restart never duplicates rows, and the mechanism must NOT be "delete backfilled rows and re-synthesize" — backfilled rows whose work has since been deleted cannot be rebuilt, so a destructive re-run would erase real history.
  - **Execution:** completion is recorded in a persistent marker; a completed pass never runs again. The pass runs as a background startup task after migrations, does not gate server readiness, and writes in small batched transactions (yielding between batches) so it never starves interactive requests on SQLite's single-writer lock (round 4).
- **REQ-011** — UI coverage. Both history surfaces (global page and per-work tab) render every event kind — new and existing — with a label, icon, and filter entry. The unknown-kind split (review round 3, resolving the REQ-011/REQ-012 contradiction): the SERVER only ever emits kinds it recognizes (REQ-012 skips the rest at read time), so the frontend's unknown-kind case is version skew — a kind the server sent but this frontend bundle has no label for; the FRONTEND renders such a row generically (raw kind text, default icon) rather than breaking the page.
- **REQ-012** — Robust reads. A history row whose stored kind the running binary does not recognize is skipped with a warning when listing — it never fails the whole query (closes ST-008's rollback hazard).
- **REQ-013** — Self-identifying payloads. Every work-attached event payload includes a snapshot of the work's title — and author where sensible — under the dedicated keys `work_title`/`work_author`, so rows remain identifiable on the global page after their work is deleted (ST-001 nulls the reference). The existing `title` key in grab-family payloads means the RELEASE title (`release_service.rs:468`, `download_poller.rs` SAB arm, `import_workflow.rs:1301`) and keeps that meaning — it is not a substitute for `work_title`. History renderers identify the work by `work_title` first. Applies to live writers and the backfill alike.

## 3. UI/Interface Design

No new surfaces. The existing global History page and per-work History tab gain: labels/icons/filter entries for the new kinds (REQ-011). Backfilled rows render identically to live rows in v1 (the `backfilled` payload field exists for a future subtle marker — Q-002).

## 4. Non-Requirements

- **`downloadCompleted`** — permanently skipped as redundant; import is the moment that matters (PO call, 2026-07-18).
- **`identityParked` and `coverUpdated` events** — deferred, not in v1.
- **qBittorrent/Transmission `downloadFailed`** — separate fast-follow; its real work is defining "failed" for a torrent (errored vs stalled vs removed), out of scope here.
- **History retention/eviction** — rows keep forever (Readarr precedent); revisit only if volume becomes a problem.
- **Per-work tab pagination** — the tab keeps its current most-recent-200 window; the global page already has load-older.
- **Author-level history** — events attach to works (or to no work, e.g. `workDeleted` after cascade); no author timeline.
- **Door-source labels on backfilled `added` rows** — the door is not reconstructible for old works; backfilled rows omit source rather than guess.
- **Reconstructing what is not persisted** — no synthesized tag/delete/merge/identity events, no enrichment timeline beyond the last success (ST-007).
- **Review dismissal** — dismissing a review-parked work's candidates defers the decision (work returns to pending); it settles nothing and records no `identityResolved` event.

## 6. Acceptance Criteria

- [ ] **AC-001** (REQ-001): Adding a new work through each creation road (interactive add, list import, Readarr, author monitor, series monitor, file-scan import) yields exactly one `added` event with the correct source label; re-adding an existing work yields none.
- [ ] **AC-002** (REQ-002): A manual refresh that applies changes yields one `enriched` event with `changed: true`; a refresh that applies nothing yields one with `changed: false` (per Q-001 default); a failing enrichment yields one `enrichmentFailed`; an identity-blocked work yields no event; a background attempt returning the deferred-merge outcome yields no event; an enrichment pass whose materialization rewrote file tags carries `tags_written: true` in its `enriched` payload.
- [ ] **AC-003** (REQ-002): A bulk refresh over N eligible works yields exactly N metadata events (one per work), and a background convergence pass that enriches a work yields exactly one.
- [ ] **AC-004** (REQ-003): A manual-import confirmation that succeeds yields one `imported` event for the work with per-file payload (work title, path, media type); a failing one yields `importFailed`. The grab road's batch-counts payload is unchanged, and both surfaces render both payload shapes. No caller-less history methods remain.
- [ ] **AC-005** (REQ-004): An import that writes tags yields one `tagWritten` event per work with attempted/succeeded counts; a tag pass where every file fails yields `tagWriteFailed` with the first error; a tag write recovered by the convergence sweep also yields its event (no unrecorded tag-write path remains).
- [ ] **AC-006** (REQ-005, REQ-006): Deleting a library file through each user door (library file-delete road, manual-import delete, secondary API) yields one `fileDeleted` event; deleting a whole work with files yields exactly one `workDeleted` event (no per-file events), and after deletion both it and the work's earlier events remain listable in the global page (work reference null); a Readarr import undo yields `fileDeleted` per removed file and `workDeleted` per removed orphan work, marked as undo; the import-internal replace cleanup yields none.
- [ ] **AC-007** (REQ-007): After merging work B into work A, B's previous history events list under A's History tab, and A has one `worksMerged` event naming B; no history row is left pointing at B.
- [ ] **AC-008** (REQ-008): Each enumerated door yields exactly one `identityResolved` event with its action named: review-candidate apply; conflict resolution via each of `KeepExisting`, `AcceptSeparate`, `ReplaceAnchor`, and `Merge`; pending-anchor affirm; and a manual user anchor edit/supersede. Review dismissal and system-initiated anchor writes (import/resolver/convergence) yield none.
- [ ] **AC-009** (REQ-009): With the history table unwritable (simulated failure), import/enrichment/delete operations still succeed and log a warning.
- [ ] **AC-010** (REQ-010): Running the backfill on a fixture library (works + grabs + files + enriched_at set, some pre-existing real history rows) synthesizes events for exactly the facts not covered by a real event — including a manual-import file newer than existing real grab-road `imported` rows AND outside the +1h coverage window (round-5 precision) — all marked `backfilled: true` with correct per-fact dates, and never duplicates a fact a real row covers; running startup again (and re-running after a simulated mid-pass crash) synthesizes no duplicates AND loses no existing backfilled rows — including backfilled rows whose work was deleted between passes; a library item just inside vs just outside the imported-coverage window is skipped vs synthesized accordingly; the server accepts requests while the pass runs.
- [ ] **AC-011** (REQ-011): Every event kind renders with label + icon on both surfaces and appears in the global filter dropdown; a frontend fed (via mocked API response) a kind string it has no label for renders it as a generic row without breaking the page.
- [ ] **AC-012** (REQ-012): A history table containing one row with an unrecognized kind still returns the remaining rows from both list endpoints, with a warning logged.
- [ ] **AC-013** (REQ-013): Every live-written and backfilled work-attached event payload contains `work_title` (distinct from any release-title `title` key); after deleting a work, its surviving rows of every event kind on the global page display the work title instead of an anonymous "—", and grab-family rows still show their release title separately.
